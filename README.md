# Форум Селан

Telegram Mini App для корпоративного общения: сотрудники видят только ветки,
разрешённые их роли, а администраторы управляют доступом внутри приложения.

## Возможности

- проверка подлинности Telegram `initData` по HMAC-SHA256 и сроку 24 часа;
- подписанная httpOnly-сессия без доверия к Telegram ID от клиента;
- серверная проверка роли при чтении каналов, истории и отправке сообщений;
- Supabase Realtime для новых сообщений;
- редактирование и удаление одобренных сотрудников в админ-панели;
- заявки на доступ через команду `/start` Telegram-боту;
- одобрение и отклонение заявок с назначением роли;
- создание, редактирование и удаление веток с настройкой доступа по ролям;
- защита от самопонижения и удаления последнего администратора;
- светлая, тёмная и системная темы с семью акцентными цветами;
- аватарки сотрудников в публичном Supabase Storage bucket;
- фото, видео и документы с прямой загрузкой в Supabase Storage;
- личные Telegram-уведомления о новых сообщениях с кнопкой перехода в ветку;
- быстрые анимации сообщений и переходов на Framer Motion;
- RLS на всех таблицах; `service_role` используется только на сервере;
- адаптивный интерфейс для Telegram WebView и Vercel.

## Требования

- Node.js 22 или новее;
- проект Supabase;
- Telegram-бот;
- аккаунт Vercel для публикации.

## 1. Установка

```bash
npm install
cp .env.example .env.local
```

Заполните `.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_ANON_OR_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_KEY
TELEGRAM_BOT_TOKEN=YOUR_BOT_TOKEN
TELEGRAM_WEBHOOK_SECRET=RANDOM_WEBHOOK_SECRET
SESSION_SECRET=LONG_RANDOM_SECRET
NEXT_PUBLIC_APP_URL=https://YOUR_DEPLOYMENT.vercel.app
```

Для `SESSION_SECRET` используйте случайную строку не короче 32 байт, например:

```bash
openssl rand -hex 32
```

`SUPABASE_SERVICE_ROLE_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` и
`SESSION_SECRET` нельзя публиковать или добавлять в переменные с префиксом
`NEXT_PUBLIC_`.
Файл `.env.local` уже добавлен в `.gitignore`.

`NEXT_PUBLIC_APP_URL` — публичный HTTPS-адрес Mini App. Он используется кнопкой
**Открыть чат** в уведомлениях. Если переменная не задана, API берёт origin
текущего запроса, но явное значение сохраняет стабильный production-домен.

`NEXT_PUBLIC_SUPABASE_ANON_KEY` предназначен только для браузерного клиента;
сюда можно поместить legacy anon key или современный publishable key вида
`sb_publishable_…`. Проект использует его для Realtime, SSR helpers и загрузки
по уже выданному signed upload token. Серверные административные операции
по-прежнему выполняются только отдельным `service_role`-клиентом.

## 2. Настройка Supabase

Создайте проект на [supabase.com](https://supabase.com), затем примените девять
миграций из `supabase/migrations/` по порядку:

1. `0001_init.sql` — основные таблицы, роли, каналы и RLS.
2. `0002_add_avatars_and_theme.sql` — настройки темы, аватарки и bucket
   `avatars`.
3. `0003_access_requests.sql` — заявки на доступ, RLS и атомарная функция
   одобрения заявки.
4. `0004_bot_registration_flow.sql` — защищённое хранение текущего шага анкеты
   Telegram-бота.
5. `0005_add_attachments.sql` — поля вложений в сообщениях и ограничения
   целостности данных. Номер `0005` используется потому, что миграция `0004`
   уже занята регистрационным сценарием бота.
6. `0006_reactions_replies_reads.sql` — реакции, ответы на сообщения,
   детальные отметки прочтения, необходимые индексы и RLS.
7. `0007_pinned_messages.sql` — поля закрепления сообщений, проверка
   целостности метаданных закрепа и частичный индекс последнего закреплённого
   сообщения в ветке.
8. `20260801074221_optimize_message_pagination.sql` — составной индекс для
   cursor pagination сообщений и индекс внешнего ключа ролей сотрудников.
9. `20260801231926_add_notification_preferences.sql` — пользовательский
   переключатель личных Telegram-уведомлений (по умолчанию включён).

Новая функциональность сообщений имеет номер `0006`, потому что `0005` уже
занят миграцией вложений.

Через Supabase CLI все миграции применяются одной командой:

```bash
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

### Применение миграций через панель Supabase

Если вы не используете командную строку:

1. Откройте проект в Supabase.
2. В левом меню выберите **SQL Editor**.
3. Нажмите **New query**.
4. Скопируйте содержимое `supabase/migrations/0001_init.sql`, вставьте его и
   нажмите **Run**.
5. Создайте ещё один запрос через **New query**.
6. Скопируйте содержимое `supabase/migrations/0002_add_avatars_and_theme.sql`
   и снова нажмите **Run**.
7. Создайте третий запрос, скопируйте содержимое
   `supabase/migrations/0003_access_requests.sql` и нажмите **Run**.
8. Создайте четвёртый запрос, скопируйте содержимое
   `supabase/migrations/0004_bot_registration_flow.sql` и нажмите **Run**.
9. Создайте пятый запрос, скопируйте содержимое
   `supabase/migrations/0005_add_attachments.sql` и нажмите **Run**.
10. Создайте шестой запрос, скопируйте содержимое
    `supabase/migrations/0006_reactions_replies_reads.sql` и нажмите **Run**.
11. Создайте седьмой запрос, скопируйте содержимое
    `supabase/migrations/0007_pinned_messages.sql` и нажмите **Run**.
12. Создайте восьмой запрос, скопируйте содержимое
    `supabase/migrations/20260801074221_optimize_message_pagination.sql` и
    нажмите **Run**.
13. Создайте девятый запрос, скопируйте содержимое
    `supabase/migrations/20260801231926_add_notification_preferences.sql` и
    нажмите **Run**.
14. Убедитесь, что все девять запросов завершились сообщением **Success**.

Первая миграция создаёт таблицы, индекс, RLS-политики, базовые роли и три
ветки. Вторая добавляет в `employees` поля `avatar_url`, `theme_preference`,
`accent_color` и создаёт хранилище аватарок.
Третья создаёт таблицу `access_requests`, закрывает её RLS-политиками от
прямого клиентского доступа и добавляет серверную транзакцию для безопасного
одобрения заявки.
Четвёртая создаёт закрытую таблицу `bot_registration_sessions`, в которой
webhook хранит только незавершённый шаг ввода ФИО.
Пятая добавляет в `messages` поля `file_url`, `file_type`, `file_name` и
`file_size`, а также разрешает отправлять вложение без текстовой подписи.
Шестая добавляет ссылку `reply_to_message_id`, таблицы `message_reactions` и
`message_reads`, индексы для пакетных выборок и закрывает обе таблицы от
прямого клиентского доступа с помощью RLS.
Миграция закреплённых сообщений добавляет в `messages` поля `is_pinned`,
`pinned_at`, `pinned_by_tg_id` и индекс `(channel_id, pinned_at desc)` только
для закреплённых строк.
Девятая миграция добавляет `employees.notifications_enabled boolean not null
default true`; существующие сотрудники продолжают получать уведомления, пока
сами не выключат их в настройках.

### Проверка bucket `avatars`

Миграция `0002_add_avatars_and_theme.sql` автоматически создаёт bucket. Чтобы
проверить его без технических инструментов:

1. В панели Supabase откройте **Storage**.
2. В списке должен появиться bucket **avatars**.
3. Откройте его настройки и убедитесь, что включён параметр **Public bucket**.
4. Максимальный размер файла bucket может быть **5 MB**; приложение принимает
   аватарки до **4 МБ**, чтобы multipart-запрос укладывался в лимит Vercel.
5. В списке допустимых типов должен быть указан `image/*`.

Публичность нужна только для показа фотографий. Загрузка выполняется серверным
API `/api/upload-avatar` после проверки Telegram-сессии; publishable key не получает
прав на загрузку, изменение или удаление объектов.

### Создание bucket `chat-attachments`

Bucket для файлов чата создаётся вручную через Dashboard:

1. Откройте **Storage → New bucket**.
2. Укажите имя **chat-attachments** без пробелов и сохраните его.
3. Откройте настройки bucket и включите **Public bucket**, чтобы изображения,
   видео и ссылки на документы открывались в сообщениях.
4. В **Storage Settings** установите глобальный лимит **50 MB**, затем задайте
   для bucket **File size limit = 50 MB**. Это дополнительный барьер на уровне
   Storage; текущая конфигурация приложения ограничивает фото до 15 МБ, видео
   до 50 МБ и документы до 30 МБ. Для видео 100–200 МБ потребуется Pro или
   более высокий тариф, увеличение лимита bucket и значения `video` в
   `ATTACHMENT_LIMITS`. См. официальную
   документацию [Storage file limits](https://supabase.com/docs/guides/storage/uploads/file-limits).
5. Если Dashboard позволяет задать список MIME-типов, разрешите:
   `image/jpeg`, `image/png`, `image/webp`, `image/gif`, `video/mp4`,
   `video/quicktime`, `video/webm`, `application/pdf`, `application/msword`,
   `application/vnd.openxmlformats-officedocument.wordprocessingml.document`,
   `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`,
   `application/zip` и `application/x-zip-compressed`.

Файл не передаётся через Next.js API. Маршрут `/api/upload/authorize` получает
только имя, MIME-тип, размер и `channel_id`, проверяет Telegram-сессию и доступ
к ветке, после чего выдаёт короткоживущий signed upload token. Сразу после
получения ответа браузер вызывает официальный метод Supabase SDK
`storage.from('chat-attachments').uploadToSignedUrl(path, token, file)`.
Ручные запросы к resumable/TUS endpoint и самостоятельная передача токена в
заголовках не используются. `/api/messages` получает только готовый публичный
URL и метаданные, а во время загрузки интерфейс показывает неопределённый
индикатор состояния.

Такой поток необходим для производственных видео: тело запроса к Vercel
ограничено примерно 4,5 МБ на уровне инфраструктуры, тогда как прямая загрузка
в Storage позволяет передавать видео до установленного лимита bucket. В пути
объекта используется только UUID и проверенное расширение; исходное имя файла
хранится исключительно в метаданных сообщения для показа пользователю.

### Добавление первого администратора

До входа в Mini App добавьте первого администратора через SQL Editor. Узнать
свой Telegram ID можно у служебного бота вроде `@userinfobot`.

```sql
insert into public.employees (tg_id, full_name, role_id)
select 123456789, 'Имя Администратора', id
from public.roles
where name = 'Администратор';
```

Замените `123456789` и имя на реальные значения. Это единственное ручное
добавление сотрудника, необходимое для запуска системы. После этого все новые
сотрудники регистрируются только через заявку Telegram-боту: ручной POST
`/api/admin/employees` отключён.

Администратор не может снять права администратора с самого себя. Система также
не позволит понизить или удалить последнего оставшегося администратора.

### Realtime и RLS

Миграции добавляют `messages` в публикацию `supabase_realtime` для новых
сообщений. Реакции и прочтения передаются серверными API через Realtime
Broadcast по теме открытой ветки. Таблицы `message_reactions` и `message_reads`
не публикуются и полностью закрыты от ролей `anon` и `authenticated`; чтение и
запись выполняются только через `service_role` после серверной проверки сессии
и доступа к ветке. Клиент применяет события только к сообщениям уже открытой
ветки.
Для систем с повышенными требованиями можно перейти на короткоживущие Supabase
JWT с разрешёнными каналами.

### Реакции, ответы и прочтения

- Долгое нажатие на сообщение открывает единое контекстное меню: реакции,
  **Ответить**, клиентское копирование текста и список прочитавших. Для
  администратора там же доступно закрепление или открепление сообщения.
  Повторный выбор своей реакции удаляет её.
- Только администратор может вызвать `POST /api/messages/[id]/pin`; сервер
  повторно проверяет актуальную роль и доступ к ветке. Последнее закреплённое
  сообщение показывается компактной полоской под заголовком канала без новой
  Realtime-подписки.
- Ответ сохраняет `reply_to_message_id`; над новым сообщением показывается
  компактная цитата. Нажатие на неё прокручивает к оригиналу, если он входит в
  загруженные последние 50 сообщений.
- Видимые чужие сообщения отмечаются прочитанными пакетным запросом
  `/api/messages/mark-read`. На своих сообщениях счётчик открывает список имён
  и времени прочтения.
- Начальная загрузка не выполняет N+1-запросов: реакции, прочтения, аватары и
  reply-превью выбираются пакетами для всех 50 сообщений. Реакции, прочтения и
  reply-цитаты вложены в основной PostgREST-запрос; справочник аватаров
  загружается параллельно и кэшируется на 30 секунд.
- История использует cursor pagination по 50 сообщений. Более ранние страницы
  загружаются кнопкой сверху без повторной выдачи уже показанных сообщений.
- Открытая ветка использует один Realtime-канал для новых сообщений и
  Broadcast-событий реакций/прочтений. Каждая строка сообщения мемоизирована,
  поэтому событие обновляет только затронутый элемент списка.

### Пользовательские настройки

Вкладка **⚙️ Настройки** доступна всем сотрудникам. Выбранная тема, акцентный
цвет, URL аватарки и выбор Telegram-уведомлений сохраняются в строке сотрудника
в таблице `employees` и загружаются при следующем входе. Изображение должно
иметь MIME-тип `image/*` и размер не более 4 МБ.

### Telegram-уведомления о сообщениях

После сохранения нового сообщения API сразу отвечает отправителю и регистрирует
фоновую задачу в request context Vercel. Она одним запросом получает сотрудников
с разрешёнными для ветки ролями и включёнными уведомлениями, исключает
отправителя и вызывает Telegram Bot API пакетами по 25 адресатов. Внутри пакета
используется `Promise.allSettled()`: блокировка бота одним сотрудником только
попадает в серверный лог и не прерывает доставку остальным. Между пакетами есть
пауза 1 секунда для соблюдения лимитов Bot API.

Уведомление содержит имя отправителя, превью до 150 символов (либо тип
вложения), ветку, время и inline-кнопку **Открыть чат**. URL получает параметр
`?channel=<uuid>`; после проверки Telegram-сессии интерфейс открывает эту ветку,
если она доступна роли сотрудника.

## 3. Локальный запуск

```bash
npm run dev
```

Supabase helpers находятся в `utils/supabase/`:

- `client.ts` создаёт browser client через `@supabase/ssr`;
- `server.ts` создаёт client для Server Components и Route Handlers;
- `middleware.ts` обновляет Supabase Auth-cookie, если она присутствует.

Основная авторизация форума остаётся Telegram-авторизацией через
`selan_session`. Middleware не выполняет лишний запрос к Supabase Auth, пока в
браузере нет отдельной Supabase Auth-сессии.

Telegram принимает только HTTPS URL. Для проверки Mini App на локальной машине
используйте HTTPS-туннель и укажите его адрес в BotFather. Обычное открытие
`localhost` покажет сообщение о необходимости запуска через Telegram, потому
что безопасного тестового обхода `initData` в проекте нет.

## 4. Развёртывание на Vercel

1. Загрузите репозиторий в GitHub/GitLab/Bitbucket.
2. В Vercel нажмите **Add New → Project** и импортируйте репозиторий.
3. Оставьте **Root Directory** пустым (корень репозитория): `package.json` и
   каталог `app/` уже находятся на верхнем уровне.
4. Добавьте все переменные из `.env.example` в **Settings → Environment
   Variables** для Production (и Preview при необходимости).
5. Нажмите **Deploy** и скопируйте итоговый HTTPS URL.

Сборка выполняется стандартной командой:

```bash
npm run build
```

## Настройка бота в BotFather

1. Откройте [@BotFather](https://t.me/BotFather) в Telegram.
2. Отправьте `/newbot`, задайте отображаемое имя и уникальный username,
   заканчивающийся на `bot`.
3. Сохраните выданный токен и внесите его в `TELEGRAM_BOT_TOKEN` в Vercel.
   Никому не отправляйте токен.
4. После успешного деплоя отправьте BotFather команду `/setmenubutton`.
5. Выберите созданного бота.
6. Введите подпись кнопки, например `Открыть форум`.
7. Введите полный HTTPS URL деплоя Vercel, например
   `https://selan-forum.vercel.app`.
8. Откройте чат с ботом заново и нажмите кнопку меню. Telegram передаст
   подписанный `initData`, приложение проверит его и создаст httpOnly-сессию.

То же можно настроить через **Bot Settings → Menu Button → Configure menu
button**. Если меняете домен, обновите URL кнопки через `/setmenubutton`.

## Настройка вебхука Telegram

Вебхук нужен, чтобы команда `/start` запускала анкету на доступ. Настраивать
его нужно один раз после публикации приложения на Vercel.

1. Убедитесь, что миграция `0003_access_requests.sql` применена.
2. Создайте случайное значение `TELEGRAM_WEBHOOK_SECRET` (латинские буквы,
   цифры, `_` и `-`) и добавьте его вместе с `TELEGRAM_BOT_TOKEN` в переменные
   Vercel, затем выполните новый deploy.
3. Подставьте токен бота, HTTPS-адрес Vercel и секрет в ссылку:

```text
https://api.telegram.org/bot{TOKEN}/setWebhook?url={VERCEL_URL}/api/telegram/webhook&secret_token={TELEGRAM_WEBHOOK_SECRET}
```

Например:

```text
https://api.telegram.org/bot123456:ABCDEF/setWebhook?url=https://selan-forum.vercel.app/api/telegram/webhook&secret_token=change_me_123
```

4. Откройте подготовленную ссылку в браузере. В ответе Telegram должно быть
   `"ok":true`.
5. Отправьте боту `/start`. Бот попросит одним сообщением ввести фамилию и имя.
6. После корректного ответа бот подтвердит отправку, а администратор увидит
   заявку в разделе **📋 Заявки на доступ**.

Токен в примере вымышленный. Не публикуйте настоящий URL с токеном в сообщениях,
скриншотах или репозитории. При смене домена Vercel повторите `setWebhook` с
новым адресом.

## Новые возможности админ-панели

В разделе **📋 Заявки на доступ** показываются только необработанные заявки.
Администратор выбирает роль и нажимает **Одобрить** — сотрудник создаётся, а
заявка атомарно получает статус `approved`. Кнопка **Отклонить** устанавливает
статус `rejected`. Количество новых заявок отображается бейджем на вкладке
админки и отдельной всплывающей плашкой. Формы ручного добавления сотрудников
нет: создать нового сотрудника можно только одобрением заявки.

Раздел **📂 Управление ветками** показывает все каналы, включая недоступные
текущей роли. Здесь можно создать или изменить название, эмодзи и список ролей
с доступом. Перед удалением показывается подтверждение; после подтверждения
ветка и все её сообщения удаляются каскадно.

## Как устроена авторизация

1. Клиент получает `initData` только из Telegram Web App SDK.
2. `POST /api/auth/verify` проверяет HMAC, `auth_date` и наличие Telegram ID в
   `employees`.
3. Сервер создаёт подписанную cookie `selan_session` с `HttpOnly`, `SameSite=Lax`
   и сроком 24 часа.
4. На каждом защищённом запросе сервер проверяет подпись cookie, заново читает
   сотрудника и роль из Supabase и только затем выполняет операцию.

Telegram ID, имя отправителя и флаг администратора никогда не принимаются от
клиента как источник правды.
